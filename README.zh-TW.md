# Vehicle Scheduling System

[English](README.md) | 中文

## 安裝與執行

只需要 Docker：

```shell
docker compose up
```

網站在 <http://localhost:8080>，API 文件在 <http://localhost:8000/docs>。

第一次啟動會自動建立資料表，並寫入初始資料：V1～V5 五台車、14 個 block 各 60 秒，班表是空的。想清空重來可以跑 `docker compose down -v`，資料會全部刪除。

跑測試：

```shell
docker compose run --rm backend pytest      # 後端，111 個
docker compose run --rm frontend-test       # 前端，84 個
```

## 資料模型

| 資料表 | 欄位 | 內容 |
|---|---|---|
| `vehicles` | `id` | 固定車隊 V1～V5 |
| `blocks` | `id`、`traversal_seconds` | 每個 block 的通過秒數，至少 1 秒 |
| `services` | `id`、`vehicle_id` | 班次，編號從 101 開始 |
| `service_stops` | `service_id`、`seq`、`station`、`departure` | 班次依序停靠的站 |

例如班次 101（Y → P1A → P2A）在 `service_stops` 裡只有三列：

```
service_id | seq | station | departure
       101 |   0 | Y       | 08:00:00
       101 |   1 | P1A     | 08:02:00
       101 |   2 | P2A     |              ← 最後一站沒有離站時間
```

**只存站，不存 block。** 規格的 12 條路段，起點和終點的組合都不重複，知道經過哪些站就推得出中間的 block，也就不會存進站和 block 對不上的資料。API 回傳時會補回完整路徑。

**算得出來的都不存。** 到站時間、電量、衝突都在每次讀取時重算。因為 block 時間可以改，改一個 block 會影響所有經過它的班次；如果把結果存起來，每次都要找出受影響的資料重算，漏一筆就會出錯。重算會多花一點時間，但以目前的設計還可接受。

**軌道結構寫在程式裡。** 路段、聯鎖組、月台是規格定死的，放在 `backend/app/domain/track.py` 當常數。`blocks` 表只是為了存可以調整的通過時間。

**時間用 `time` 型別。** 這是單日時刻表，不需要日期。程式計算時換成「從午夜起算的秒數」。

## API

全部在 `/api` 底下，欄位細節看 `/docs`。

| API | 用途 |
|---|---|
| `GET /api/track` | 軌道：車站、block、路段、聯鎖組 |
| `GET /api/vehicles` | 車隊 |
| `GET /api/blocks`、`PUT /api/blocks` | 讀取、一次更新全部 block 的通過時間 |
| `GET /api/services`、`GET /api/services/{id}` | 班次，含完整路徑和到站時間 |
| `POST /api/services`、`PUT /api/services/{id}` | 新增、修改班次 |
| `POST /api/services/delete` | 批次刪除，例如 `{"ids": [101, 103]}`；有一個不存在就都不刪 |
| `GET /api/conflicts` | 目前所有衝突 |
| `GET /api/timeline` | 每台車整天的位置和電量，給播放畫面用 |
| `GET /api/schedule/limits` | 自動排班：最短能排幾分鐘、更短為什麼不行 |
| `POST /api/schedule/generate` | 自動排班：產生班表，取代現有班次 |

新增班次只送站和離站時間，回傳時補上路徑和到站時間：

```json
POST /api/services
{ "vehicle": "V1", "stops": [{ "at": "Y", "departure": "08:00:00" }, { "at": "P1A", "departure": "08:02:00" }, { "at": "P2A" }] }

→ 201
{
  "id": 101, "vehicle": "V1",
  "path": ["Y", "B1", "P1A", "B3", "B5", "P2A"],
  "stops": [
    { "at": "Y",   "arrival": null,       "departure": "08:00:00" },
    { "at": "P1A", "arrival": "08:01:00", "departure": "08:02:00" },
    { "at": "P2A", "arrival": "08:04:00", "departure": null }
  ]
}
```

班次本身不合法（路線不存在、停靠不到 1 秒、到站超過午夜、車輛不存在）會回 422，`loc` 指出是哪一站的哪個欄位。班次本身沒問題、只是跟其他班次衝突的，照樣存進去，由 `GET /api/conflicts` 標出來。衝突有 10 種：

| 種類 | 意思 |
|---|---|
| `block` | 兩台車同時在同一個 block |
| `interlocking` | 兩台車同時在同一聯鎖組的不同 block |
| `platform` | 兩台車同時在同一個月台 |
| `vehicle_overlap` | 同一台車的兩個班次時間重疊 |
| `discontinuity` | 同一台車上一班的終點和下一班的起點接不起來 |
| `not_returned` | 最後一班沒有回到 Y |
| `dwell_too_short` | 改了 block 時間後，到站沒有早於離站 |
| `past_midnight` | 改了 block 時間後，到站超過午夜 |
| `low_battery` | 電量低於 30 且不在 Y |
| `insufficient_charge` | 從 Y 出發時電量不到 80 |

## 設計取捨

### 只填離站時間，到站時間由系統算

到站時間等於「上一站離站 + 中間 block 的通過時間」，所以我讓使用者只填離站時間。另外考慮過兩種做法：到站、離站都填，很容易跟 block 時間對不上；只填出發時間和每站停多久，改 block 時間時延誤會一路推到最後一站。

例如 `P1A 08:02 離 → P2A 08:04 到、08:06 離 → P3A 08:08 到`，把 B5 從 60 秒改成 90 秒：

| | 填離站時間（採用） | 填停多久 |
|---|---|---|
| P2A 到站 | 08:04:30 | 08:04:30 |
| P2A 離站 | 08:06，不變 | 08:06:30 |
| P3A 到站 | 08:08，不變 | 08:08:30 |

延誤由停站時間吸收，公布的離站時間不變，比較接近真實時刻表。缺點是延誤太大時，到站會晚於離站，例如 B5 改成 200 秒，08:06:20 才到 P2A。這時會標出 `dwell_too_short` 讓使用者修正。

### 衝突先標出來，不直接擋下

只有單一班次本身不合法才擋，其他衝突都是好幾個班次湊在一起才出現的，所以先存再標。因為編輯過程本來就會暫時出現這些狀態：例如刪掉三個連續班次中間的那個，刪完當下前後兩班一定接不起來。全部擋下的話，使用者連刪都刪不掉。代價是資料庫可能存著有問題的班表，所以畫面要清楚標出問題和原因。

### 自動排班用固定環線

所有車跑同一圈 `S1 → P2A → S3 → P2B → S1`，每站停 10 秒，用剛好夠的車數平均排開。電量不夠時回 Y 充電，由充好電的車接手。產生後再跑一次衝突檢查，有衝突就不交出結果。

規則固定，結果一定沒有衝突，也好測。畫面上的最短間隔是用同一個產生器從 1 分鐘往上試出來的，跟實際結果一致。缺點是車距平均分配，可能比要求的短（間隔填 6 分鐘，實際每 4 分 20 秒一班）；也不會微調個別班次，所以某些 block 時間下，最短間隔會比理論值長一點。

### 每個中間站至少停 1 秒

佔用時間用 `[進入, 離開)` 判斷，剛好接上不算衝突。如果允許停 0 秒，車在月台的區間是 `[t, t)`，什麼都抓不到。例如兩台車都在 08:00:00 到 P1A、都停 0 秒，系統不會報衝突。

規定至少停 1 秒，區間就不會是空的，block、聯鎖、月台都用同一套判斷。改用閉區間會把剛好接上也當成衝突；把 0 秒當特例處理則要多一種判斷。代價是不能表示「通過不停」，但規格沒有這個需求。

## 假設

- 單日時刻表，班次不能跨午夜。每天開始時所有車都在 Y，電量 80。
- 規格沒說車隊有幾台，我設定成固定 5 台（V1～V5），由初始資料寫入。新增班次時用下拉選單選，避免打錯字變成一台新車。
- 班次編號由系統產生，從 101 開始。
- 第一站沒有到站時間，最後一站沒有離站時間。中間站至少停 1 秒；同一台車兩個班次之間也至少隔 1 秒。
- 每一段路徑都要是鄰接表裡的一條，不能在 block 中間掉頭；在月台折返可以，例如 `Y → P1A → Y`。
- Y 只能在路徑頭尾，經過 Y 要拆成兩個班次，充電才算得清楚。
- 最後一班要回到 Y，否則標 `not_returned`。
- 車當作一個點。剛好接上不算衝突，也沒有另外留安全間隔。
- 月台也算佔用，同一時間只能有一台車（Y 不限），否則後車可以從停站的前車旁邊穿過去。
- 同一個 block 重疊只報 block 衝突；聯鎖衝突只報同組裡不同的 block。
- 進入 block 時扣 1 電，停站不扣。出廠時看的是離開 Y 之前的電量。
- 在 Y 每滿 12 秒充 1，最多 100。低電量每趟出車只報一次。
- 班次接不起來之後，就不再推算電量，因為不知道車有沒有回去充電。
- 自動排班的開始、結束時間，指的是車從 Y 發車的時段，所以第一台車 08:00 才從 Y 出發，不會提早出廠。但從 08:00 起，每一站都要在一個間隔內等到車。最遠的 S3 要等第一台車從 Y 開過去。以預設值來算，經過 5 個 block（預設各 60 秒），中間在 P1A、P2A 各停 10 秒（自動排班預設的停靠時間），08:05:20 才到 P3A，所以間隔最短是 6 分鐘。block 時間或停靠時間調短，最短間隔也會跟著變短。
- 自動排班產生時會整份取代原本的班表；排不出來的話，原本的班表不會被動到。
- 單一使用者，不需要登入；只支援電腦版。
